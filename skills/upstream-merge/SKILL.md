# 把上游改动合入自有 fork

## 何时用

- 上游发布了新 tag/commit，需要在本 fork 里跟进；
- `git merge origin/master` 报冲突，且冲突落在文档、生成物、或两边都改过的同一函数上；
- 没有冲突但担心"合进来了却没保住 fork 功能"（缺测试、产物没重建、文案被覆盖）。

不适用：单纯改本 fork 自己的代码（直接开 `feat/` 分支即可）。

## 前置检查

1. `git fetch origin --tags`，确认 `origin/master` 与目标 tag 一致；
2. `git branch --show-current` 必须干净，`git status` 无未提交改动；
3. 确认当前分支的上游跟踪是**自己的远端**，不是 `origin`：
   `git rev-parse --abbrev-ref master@{upstream}` 应为 `<fork-remote>/master`；
4. `git log --oneline <上次同步点>..origin/master` 看清上游改了什么范围。

## 阶段 1 · 预演（不动工作树）

```sh
git merge-tree --write-tree master origin/master
```

- 输出干净 → 这次是"能直接合"的类型，仍要走阶段 4–6；
- 输出冲突列表 → 逐路径登记冲突，按阶段 3 的归属表先写下裁决，再动手。

同时预判两类**没有冲突但会出错**的情况：

| 现象 | 后果 | 处理 |
| --- | --- | --- |
| 上游重命名/删除了 fork 依赖的 API | 合并后编译不过或行为静默改变 | 先适配新 API，再把 fork 功能放回去（阶段 3.1） |
| 上游改写了 fork 条目所在的同一段文档 | 无文本冲突但语义覆盖 | 用"上游主干 + fork 段落"结构重写该段 |
| 上游更新了生成物 | 与本 fork 产物冲突 | 不裁决，只重建（阶段 4） |

## 阶段 2 · 建同步分支

```sh
git switch -c sync/upstream-v<上游版本> master
git merge --no-ff --no-edit origin/master
```

- 同步分支**只装上游内容**；fork 功能已经在 `master` 里，合并进来即可，不要在这条
  分支上顺手写新功能；
- 一次同步只用一条分支，不要连着合两个上游版本。

## 阶段 3 · 按所有权裁决冲突

判据是"这段代码归谁负责"，不是"哪个版本新"。

| 冲突位置 | 裁决 | 动作 |
| --- | --- | --- |
| 上游的领域（核心逻辑、宿主契约适配、锚点、装配流程） | 上游赢 | `git checkout --theirs <path>`，然后读一遍确认 fork 没有在此处有独立实现 |
| fork 的领域（自有功能文件、自有 UI 段落、自有配置项） | fork 赢 | 保留本地内容；若上游同文件有无关改进，手工移植上游部分 |
| 生成物（产物 bundle、sourcemap） | 谁都不赢 | `git checkout --theirs` 后按阶段 4 重建 |
| 版本与依赖能力声明（`engines`、宿主依赖清单） | 上游赢 | 直接取上游 |
| 身份字段（仓库地址、主页、issue 地址） | fork 赢 | 合并后逐条改回本 fork |
| 同一段文档被两边改 | 上游主干 + fork 段落 | 上游措辞在前，fork 独有条目原样接在其后 |
| 双方都"插入一行"的配置 | 取并集 | 两条都留，改 id 冲突则改名 |

### 3.1 上游改了 fork 所依赖的结构

不要硬保 fork 的旧写法。做法：

1. 先只取上游版本，让编译与测试通过（此时 fork 功能暂时消失或报错）；
2. 把 fork 功能的**意图**重新实现到上游的新结构上（不是把旧代码贴回去）；
3. 用测试与真机验证证明功能回来了；
4. 在 `docs-work/pending.md` 记录这次适配：哪个接口变了、fork 功能如何等价实现。

如果重新实现的成本明显超过收益，停下来问维护者，而不是悄悄降级掉功能。

## 阶段 4 · 重建产物

- 任何生成物冲突都以重建收尾，禁止手改；
- 重建前确认依赖树完整（`pnpm install --force`），否则报错会被误读成代码问题；
- 重建后核对产物里确实含有上游的新逻辑与 fork 的旧逻辑：
  用 `git diff --stat` 看改动规模，再 grep 几个特征符号确认双方都在。

## 阶段 5 · 验证链

按顺序跑，前一步不过不进入下一步：

| 顺序 | 检查 | 通过判据 |
| --- | --- | --- |
| 1 | 依赖安装 | 无 `ERR_MODULE_NOT_FOUND`、无 `not recognized` |
| 2 | 类型检查 | 报错数 **不高于基线**；把基线与本次结果逐条对比，新增即失败 |
| 3 | 测试 | 全绿；上游新增的用例也必须在里面 |
| 4 | 构建 | 退出码 0，产物时间戳更新 |
| 5 | 真机验收 | 上游若提供集成脚本，跑通；跑不起来（缺源码树等）就登记到 pending，**不要写成通过** |

## 阶段 6 · 落地

```sh
git switch master
git merge --no-ff sync/upstream-v<版本>
git tag -a v<版本>-fork-sync -m "sync upstream <版本>"
git push <fork-remote> master
git push <fork-remote> refs/tags/v<版本>-fork-sync
```

- 合并后检查身份字段是否被改回上游地址；
- 更新 fork 维护文档里的版本对应关系（上游版本 → 本 fork 版本）；
- 若本次同时合入了 fork 功能，按语义升版本（仅同步 = patch，同步 + 功能 = minor），
  版本号与文档里的安装标签同一次提交改完。

## 回滚

同步坏了，不要 `reset` 发布线：

```sh
git revert -m 1 <合并提交或同步 tag>
```

随后重打一个新 patch 版本。已发布的 tag 永不移动。

## 常见失败模式

| 失败 | 症状 | 根因与纠正 |
| --- | --- | --- |
| 生成物被手工解决冲突 | 运行时报错、行为与源码不符 | 产物必须重建；冲突一律 `checkout --theirs` 再 build |
| 只跑了测试就宣布成功 | 测试全绿但界面回退 | 测试不覆盖 UI 注册点；补一次真机目视 |
| 上游功能"合进来了"但 fork 特性消失 | 无冲突、测试绿、功能没了 | 上游重写了同一段；按阶段 3.1 在新结构上重实现 |
| 身份字段回退 | 安装命令指向上游 | 合并后逐条核对仓库地址三个字段 |
| 类型检查有新增报错被当基线放过 | 隐患被掩盖 | 基线与本次结果逐条对比，不只看总数 |
| 一次同步分支合了两个上游版本 | 冲突无法归因、回滚粒度失效 | 一条同步分支只做一次同步 |
| 跟踪分支指向上游 | 顺手 `git push` 推错仓库 | 克隆后第一件事核对 `@{upstream}` |

## 不做

- 不向上游提 PR、不向上游推送任何分支或 tag（本仓库的治理原则）；
- 不 rebase / force-push 发布线；
- 不改测试断言去迁就合并结果——先判断是夹具过期还是代码错了；
- 不把手写的"合并说明文档"留在版本区：过程记进 `docs-work/`，最终真相写进
  `docs/fork-policy.md` 与模块设计文档。
